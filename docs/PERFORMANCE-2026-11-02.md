# 宝可梦 SA：MLP1 卡顿诊断（2026-11-02）

## 结论

当前地图持续卡顿主要受单核 CPU 上的 Ruby 地图更新限制。瓦片渲染、
MakerStudio 图形扩展和角色阴影形成主要热点。现有证据不支持将内存容量、
GPU 算力或温度降频作为这轮持续卡顿的首要原因。

本轮仅进行测量，未部署新的画质或游戏逻辑优化。静态战斗精灵补丁继续禁用，
计时兼容修复及原 JoiPlay 地图补丁保留。未修改存档。

## 设备观测

- 系统内存约 955 MB，采样时可用约 316–323 MB，游戏 RSS 约 487 MB。
- 地图场景 RGSS 线程长期接近一个 CPU 核心的满负载；一次 30 秒区间累计
  约 28.21 CPU 秒。该区间主要缺页次数没有增加。
- CPU 频率 1.992 GHz，温度约 53–55℃，未观察到该区间降频。
- 对应 GPU 负载读数约 6–7%，频率 800 MHz。
- 不同阶段的五秒帧计数区间约 18–59 FPS，游戏目标帧率为 60。
  地图调用栈对应的多个区间约 30–34 FPS；较后区间约 40–45 FPS。
  场景和移动状态变化，且方法计时窗口会额外拖慢游戏，不能作为严格基准。
- 启动/读档存在 frame_count 跳变，异常的数千 FPS 区间已排除。

## 两种独立采样

1. 原生 perf_event CPU 指令采样：第一轮 5,577 个用户态样本，约 80.6%
   位于 mkxp-z 可执行文件，最集中的符号为 Ruby VM 解释执行及其方法、
   实例变量和哈希查找函数。约 13.3% 位于 Mali 用户态驱动。
   第二轮 7,252 个样本同样显示 Ruby VM 执行为首要热点。
   可执行文件包含 Ruby 和原生渲染器，不能将该文件占比全部算成 Ruby。
2. Ruby 方法计时：使用线程限定的 TracePoint call/return，记录线程 CPU 时间，
   每约 15 秒采集 1 秒，共 12 次。没有包装 Graphics.update、强制 GC 或改写
   游戏方法。普通 Ruby 后台栈采样因 GVL 调度偏向 Graphics.update，因此
   没有用其样本比例推算脚本耗时。

TracePoint 自身开销显著；以下数字用于定位热点及重复调用，不能直接作为正常
运行下的每帧毫秒数或预计提速百分比。inclusive 时间包含子调用，不可相加。

## 地图方法热点

移动窗口 20:57:03（约 1.1 秒，含诊断开销）：

| 方法 | 完成调用数 | inclusive CPU ms | self CPU ms |
| --- | ---: | ---: | ---: |
| TilemapRenderer.update | 6 | 337.50 | 140.60 |
| MakerStudio.refresh_tile_coordinates | 4,419 | 148.38 | 103.02 |
| Overworld Shadows EX 的阴影 update | 399 | 140.56 | 68.29 |
| Game_Map.update | 7 | 149.12 | 56.69 |
| MakerStudio.update_extended_pool | 6 | 62.47 | 46.03 |

随后多个窗口重复出现相同热点。20:58:19 的窗口中：

- 阴影 update 665 次，inclusive 235.39 ms，self 114.65 ms。
- TilemapRenderer.update 7 次，inclusive 137.34 ms，self 90.91 ms。
- 扩展层 update_extended_pool 6 次，inclusive 61.99 ms，self 45.84 ms。
- 公共事件 update 3,500 次，对应约 500 次检查/地图帧。
- 角色图形更新约 665 次，对应约 95 个角色/地图帧。
- GC 该窗口记录为 1 次、19 ms；多个相似窗口仍由地图和阴影计算主导。

源码核查发现原地图渲染器逐帧遍历可见区域三层瓦片；MakerStudio 在坐标更新、
扩展层和角色图形上叠加处理。阴影插件逐个更新位置、深度、透明度和可见性，
并调用角色坐标计算。它们都会随可见瓦片、事件和角色数增加而增加 CPU 工作量。

## 优化顺序

1. 单独测试关闭角色脚下阴影及动态阴影：这是可降低画质、且与热点直接相关的
   实验。保留事件本身更新；用相同地图/路线比较开启与关闭，不能先承诺收益。
2. 优化地图渲染：合并/缓存重复坐标计算、避免无变化瓦片和扩展层的重复处理，
   或逐步移到原生实现。保留旋转、桥梁、反射、遮挡和地图拼接语义。
3. 减少公共事件空检查、角色图形和坐标的重复计算。不得直接跳过所有屏外事件，
   以免破坏并行事件、移动路线和剧情触发。
4. 之后再评估独立的稳定帧率模式及跳帧。需确认游戏时间/移动速度不变，
   不能仅降低全局帧率来宣称优化。

Ruby 3.1 的随包 YJIT 源码仅支持非 Windows x86_64，当前 AArch64 设备不能
通过简单开启 YJITEnable 获得加速。升级 Ruby/JIT 属于另一项需兼容测试的改动。

## 后续优化试验

第一版可选性能配置关闭了角色脚下阴影和动态角色投影，并合并了基础引擎与
MakerStudio 的瓦片坐标更新。用户确认画面正常，但地图移动无明显改善。
21:17 的地图 78 走动区间仍出现约 16–24 FPS；这项试验不足以解决卡顿。
同一地图不同位置和移动状态的帧率差异很大，不能用最高帧率代表整体收益。

第二版增加 batched_tiles：每张可见地图取一次地图数据，复用可见单元遍历缓存，
减少范围/枚举器和临时数组的生成。只替换 MakerStudio 捕获的基础瓦片遍历方法，
外层扩展层、照明、雾、地图阴影和游戏事件更新保持运行。

验证包括 720 组坐标/变换等价检查、关闭/无效配置回退、动画瓦片与桥梁测试，
以及 48 组场景序列与本机现有引擎原方法的逐项输出对照。主机模拟 3,000 次
瓦片遍历耗时由 1.372 秒降至 0.827 秒；这是测试替身上的循环微基准，不能
折算为掌机游戏 FPS。第二版已部署，掌机效果尚待重启后的同路线验证。

可选配置位置为 USERDATA_PATH/mkxp-z/<game-key>/pokemon-sa-performance.conf。
enabled=off 并重启可整体回退；shadows=on、tile_coordinates=off、batched_tiles=off
可分别回退三项。第一版和第二版均未使用静态精灵资源，也未修改存档。

用户反馈第二版仅略有改善。第二版日志中地图 78 仍有约 18–23 FPS 的走动区间；
不同地图、菜单与战斗混杂，尚不能得出严格的同路线提速百分比。

第三版针对新发现的全局工具函数：Luka's Scripting Utilities 重写了
Hash.has_key?，对每次查询调用 keys.include?，生成并扫描完整键列表。
GameData 查询、地形判断和地图寻路会进入这条路径。已为原生 Symbol/Integer
键的成功查询增加 native key? 快速路径；其他类型和未命中的查询继续调用原方法，
保留多参数、==/eql? 差异和 identity hash 行为。532 组等价性检查通过。
主机微基准中 2,000 键字典的 10 万次命中查询由 1.7654 秒降至 0.0199 秒；
这不代表游戏整体提速比例。修复已部署，实际效果待重启验证。

用户反馈第三版无明显改善。21:56 的地图 33 走动区间仍约 19–21 FPS，
进程 CPU 约 110–114%，RSS 约 461 MiB、可用内存约 333 MiB。
稳态走动的 GC 累计时间每 5 秒只增加约 50–70 ms，不能解释整个约 50 ms/帧。
前三次试验未解决卡顿，不应把主机微基准改善当成掌机整体提速。

下一轮改用原生逐帧计时，避免 Ruby 线程栈采样的 GVL 偏差和 TracePoint 开销。
`patches/mlp1-frame-trace.patch` 在环境变量 `MKXPZ_LEAF_FRAME_TRACE` 非空时启用，
默认关闭；启动器只在每游戏 userdata 下有 `frame-trace.enabled` 时导出日志路径。
每 120 帧或接近缓冲区满时批量写 CSV，最多记录 240 秒，不挂钩 Ruby 更新方法。
记录 Graphics.update 之间的间隔、update 总耗时、场景合成、限帧等待和 swap 等待。
间隔包含脚本、绑定及 GVL 等工作，不能直接称为纯 Ruby 时间；合成/等待是 update
的子区间，不能重复相加。GPU 异步执行也可能将开销推迟到后续 GL 调用。
可用 `python3 scripts/analyze_frame_trace.py <CSV>` 分段分析并与场景日志对照。

同时发现启动器强制 `vsync=true` 覆盖了游戏的 `vsync=false`。这只是待验证的
显示节奏影响因素，尚未改动该设置；不降低全局目标帧率或启用跳帧掩盖计算问题。

## Q 加速导致顿感的补充定位

用户补充：不开 Q 时可以接受，主要顿感发生于开启加速后。此前采样未记录
`$GameSpeed`，不能将所有低帧率都归为正常速度。新增监视日志将记录加速档位。
原生计时显示，重载路段 update 间隔约 40–50 ms，场景合成约 7–9 ms，
swap 约 0.3 ms，限帧等待约 0.08 ms；显示同步等待不是该样本的主要耗时。
站立区间呈现约 26 FPS，走动多次降至 16–18 FPS，采样时加速状态待后续明确。

本机现有 Better Speed Up 源码使用 `[1,2,3]` 档位，在 Graphics.update 中
只让每 N 次调用中的一次进入原生绘制，其余提前返回。游戏逻辑和 Ruby 地图
渲染器仍每次循环运行，所以 CPU 负担没有随原生跳绘制同比减少。

增加可回退的 `speedup_render`：仅在已识别的加速插件/MakerStudio 组合且处于
地图加速时，跳过不会在下一次呈现中使用的中间瓦片/扩展层更新。Scene_Map
顺序是先 Graphics.update 再地图更新，因此在最后一个跳绘制 tick（phase=N-1）
准备地图，供下一次呈现使用，不能反过来只在 phase=0 更新。
不跳过玩家、事件、解释器或角色更新；首次调用、显式 refresh、地图变更、
加速档位变更、菜单/战斗及回地图时强制更新。正常速度保留每次地图更新。
地图纯视觉动画在加速时的推进次数会减少，实际画面和收益需设备验证。
已通过 400 次呈现状态与原循环对照，以及 1x/2x/3x、切档、刷新、传送、
菜单/战斗边界检查。未部署另备的分段方法计时器。
